# Internationalization

Translation of the application and of every text the components write themselves (F11), exported by
`@midnight-indigo/ui/i18n`. It is built on [i18next](https://www.i18next.com) and
[react-i18next](https://react.i18next.com), optional peers that only this subpath loads:

```sh
pnpm add i18next react-i18next
```

| Export                                           | Use it for                                                                      |
| ------------------------------------------------ | ------------------------------------------------------------------------------- |
| `I18nProvider`                                   | The locale, messages, time zone and currency of a React tree                    |
| `useI18n(namespace?)`                            | `t`, `rich`, `plain`, `changeLocale`, the formatters and the instance           |
| `RichMessage`, `createRichTranslator(t)`         | Messages with tags (`<strong>`, links) ([rich-messages.md](./rich-messages.md)) |
| `useFormatters()`                                | Numbers, currencies, dates, relative times, lists and file sizes                |
| `createI18n(options)`                            | A ready i18next instance outside React (Server Components, scripts, tests)      |
| `createFormatters(options)`                      | The formatters outside React                                                    |
| `libraryNamespace`, `libraryResources`           | The texts of the components (`midnight-indigo` namespace), pt-BR and en-US      |
| `englishMessages`, `brazilianPortugueseMessages` | The same texts, as a starting point for a new locale                            |
| `mergeResources`                                 | Deep merge of resources, key by key                                             |

Without a provider, the components keep working in English, and their `labels` prop still overrides any text.

## Messages

Messages are plain JSON, by locale and namespace. The organization of the keys is up to the application; grouping by
domain is recommended, not required:

```json
{
	"text": { "name": "Nome", "search": "Pesquisar" },
	"user": { "name": "Nome do usuário", "email": "Endereço de e-mail" }
}
```

Keys are always camelCase. Plural categories and contexts are **nested objects**, never `_one`/`_other` suffixes: the
provider sets the i18next `pluralSeparator` and `contextSeparator` to `.`.

```json
{
	"inbox": {
		"messages": {
			"zero": "Nenhuma mensagem",
			"one": "{{count, number}} mensagem",
			"many": "{{count, number}} de mensagens",
			"other": "{{count, number}} mensagens"
		}
	},
	"sort": { "ascending": "Crescente", "descending": "Decrescente" }
}
```

- `t('inbox.messages', { count })` picks the category of `Intl.PluralRules` for the locale (`zero` is used for 0 when it
  exists). Portuguese, Spanish and French have `many` (millions), so give it in those languages.
- `t('sort', { context: 'ascending' })` picks a variant.
- `{{name}}` interpolates without HTML escaping (React escapes what it renders). Never build a sentence by concatenating
  translated fragments: interpolate into a whole sentence, and format part of it with tags
  (`"Hello <strong>{{name}}</strong>"`, rendered by `rich`; see [rich-messages.md](./rich-messages.md)).
- `{{value, number}}`, `{{value, datetime}}`, `{{value, currency}}`, `{{value, list}}` and `{{value, relativetime}}`
  format inside a message. `datetime` uses the configured time zone and `currency` the configured currency; options go
  in the message (`{{value, currency(USD)}}`) or in `formatParams`.

## The provider

```tsx
<I18nProvider
	locale='pt-BR'
	fallbackLocale='en-US'
	resources={{
		'pt-BR': { translation: brazilianMessages },
		'en-US': { translation: englishMessages },
	}}
	timeZone='America/Sao_Paulo'
	currency='BRL'
>
	{children}
</I18nProvider>
```

| Prop               | Meaning                                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------------------- |
| `locale`           | Locale to render. Given by the application (route, cookie, setting); never detected                     |
| `fallbackLocale`   | Locale(s) for keys the locale lacks                                                                     |
| `resources`        | Bundled messages, merged over the texts of the library                                                  |
| `loadMessages`     | `(locale, namespace) => Promise<Messages \| undefined>` for messages loaded on demand (e.g. `import()`) |
| `namespaces`       | Namespaces of the application; defaults to those in `resources`, or `translation`                       |
| `defaultNamespace` | Namespace of `t` when the key names none; defaults to the first one                                     |
| `timeZone`         | IANA time zone of the dates. Required to format dates                                                   |
| `currency`         | ISO 4217 code. Required to format currencies without their own `currency`                               |
| `onMissingKey`     | Called for a key found in no locale; defaults to `console.warn`                                         |
| `options`          | Any other i18next option, applied last                                                                  |

The locale, the time zone and the currency are independent: none is inferred from another, nor from the runtime. A
date formatted without a time zone, or a currency without a code, throws `FormattersConfigurationError` instead of
silently using the time zone of the machine, which differs between the server and the browser.

A missing key is reported (once per key) and renders the key itself, so the interface stays usable. A text of the
library that does not resolve keeps the English default of the component.

`useI18n()` reads the namespace given to it, or the default one; `'billing:plan'` reaches another namespace. The
provider shares its instance with react-i18next, so `useTranslation` and `Trans` work inside it too.

## Texts of the components

Each component reads its texts in this order: its `labels` prop, then the provider, then its English default. The
provider builds them from the `midnight-indigo` namespace, which the library ships in **pt-BR** and **en-US** with
every text covered (a test checks the keys and plural categories of both). The keys are the component names, as in
[`englishMessages`](../src/i18n/messages/en-us.ts):

```json
{
	"dialog": { "close": "Close" },
	"dataTable": {
		"sorted": {
			"ascending": "Sorted by {{column}}, ascending",
			"descending": "Sorted by {{column}}, descending"
		},
		"resultCount": {
			"zero": "No rows",
			"one": "{{count, number}} row",
			"other": "{{count, number}} rows"
		}
	}
}
```

- **Override** a text: give the same key in your resources; the rest of the namespace stays.

  ```ts
  resources: { 'pt-BR': { 'midnight-indigo': { dialog: { close: 'Sair' } } } }
  ```

- **Add a locale**: give its messages (start from `englishMessages`). Texts it lacks come from `fallbackLocale`.

  ```ts
  resources: { es: { translation: spanish, 'midnight-indigo': { dialog: { close: 'Cerrar' } } } }
  ```

- **One instance only**: `labels={{ close: 'Sair' }}` on the component still wins.

Accessible names, live announcements (sorting, pages, results, errors), loading and empty states and native validation
messages of `Form` are all covered. File sizes of `FileUpload` are formatted with the units of the locale (`1,5 MB`).
The date pickers keep their own locale: pass the date-fns locale and the MUI X `localeText` of the same language to
`DatePickersProvider` (see [forms.md](./forms.md)).

## Next.js App Router and hydration

The server and the browser must render with the same locale, messages, time zone and currency, or React reports a
hydration mismatch. Pass all of them as props from the server:

```tsx
// app/[locale]/layout.tsx (Server Component)
import { AppI18nProvider } from '#src/i18n/app-i18n-provider.tsx';

const LocaleLayout = async ({
	children,
	params,
}: LayoutProps<'/[locale]'>): Promise<ReactElement> => {
	const { locale } = await params;
	const messages: Messages = (await import(`#src/messages/${locale}.json`)).default;

	return (
		<html lang={locale}>
			<body>
				<AppI18nProvider locale={locale} messages={messages}>
					{children}
				</AppI18nProvider>
			</body>
		</html>
	);
};
```

```tsx
// i18n/app-i18n-provider.tsx
'use client';

import { I18nProvider } from '@midnight-indigo/ui/i18n';

export const AppI18nProvider = ({
	locale,
	messages,
	children,
}: AppI18nProviderProps): ReactElement => {
	return (
		<I18nProvider
			locale={locale}
			fallbackLocale='en-US'
			resources={{ [locale]: { translation: messages } }}
			timeZone='America/Sao_Paulo'
			currency='BRL'
		>
			{children}
		</I18nProvider>
	);
};
```

- Read the locale from the route (or a cookie) on the server; do not detect it in the browser (`navigator.language`)
  during render.
- Put the messages of the first render in `resources`. `loadMessages` and `onMissingKey` are functions, so they only
  go in from a Client Component, as above; use `loadMessages` for locales the user switches to later.
- Give `timeZone` explicitly (the user's setting, or the zone of the business), never the zone of the server.
- Set `<html lang={locale}>` in the root layout.
- In a Server Component, translate with `createI18n` (one instance per request; never a module-level singleton shared
  between requests): `const i18n = await createI18n({ locale, fallbackLocale: 'en-US', resources }); i18n.t('key')`.

Changing the `locale` prop changes the language of the instance; `useI18n().changeLocale(locale)` does the same from a
component, loading its messages first. A test renders the provider on the server in UTC, hydrates it in another time
zone and checks that no mismatch is reported.

`templates/nextjs-starter` is the complete setup, in pt-BR and en-US: the locale is the first segment of the URL
(`/pt-br/orders`), every page is built once per locale, a `proxy.ts` sends a path without one to the language chosen
in the language links (a cookie) or preferred by the browser (`Accept-Language`), Server Components translate with a
`createI18n` instance per request and locale (React `cache`), the browser receives the messages of its locale only, and
the 404 page of a missing path is translated too (`app/global-not-found.tsx`). Its tests render every page in both
languages and check that no message key is left untranslated.
